2. BLOCKING ERRORS  (app cannot do its advertised job)
================================================================================

[E1] DesktopService never routes frames -> chat can never work
  File: desktop/services/DesktopService.java:33-39
  Problem: ConnectionManager is constructed with three no-op callbacks:
      conn -> {},          // onConnectionEstablished
      conn -> {},          // onConnectionClosed
      frame -> {}          // onFrameReceived
  The onFrameReceived callback is the ONLY path by which inbound frames reach
  the application. Because it is empty, ChatManager.handleFrame() and
  TransferManager.handleFrame() are never invoked. Even after implementing the
  chat methods, no message would ever arrive.
  Fix: route frames by MessageType into ChatManager / TransferManager /
  PairingManager / DiagnosticsManager. Register the same routing as a real
  onFrameReceived lambda, and use onConnectionEstablished/Closed to update UI
  state and the DiagnosticsManager connection table.

[E2] DesktopService.connectToDevice() is empty -> Connect button is a no-op
  File: desktop/services/DesktopService.java:124
      // TODO: Implement connection logic
  Fix: look the device up via discoveryManager.getDevice(deviceId), then
  connectionManager.connect(device.ipAddress(), device.tcpPort()), then
  sendHello() with the real local deviceId, name and public key so the peer can
  map the connection to a deviceId. Without sendHello, getConnection(deviceId)
  can never match and all outbound sends fail the "not connected" check.

[E3] ChatManager.sendTextMessage() and sendGroupMessage() are empty
  File: core/messaging/ChatManager.java:101 and :105
      private void sendTextMessage(Connection conn, TextMessage message) {
          // Send text message frame
      }
  sendMessage() does all the surrounding bookkeeping correctly (resolves the
  connection, builds the TextMessage, stores it, registers a PendingAck, fires
  onMessageSent) and then calls this empty method. So the UI will appear to
  "send" a message that never leaves the machine.
  Fix: serialize TextMessage to JSON (Jackson ObjectMapper + JavaTimeModule is
  already the pattern used in DiscoveryListener) and call
  connectionManager.sendFrame(conn, Frame.create(MessageType.TEXT_MESSAGE.value(),
  (byte) 0, UUID.randomUUID(), json.getBytes(UTF_8))).
  Same for GROUP_MESSAGE (0x33).

[E4] ChatManager.handleFrame() is empty -> inbound chat dropped
  File: core/messaging/ChatManager.java:93
      public void handleFrame(FrameCodec.Frame frame) {
          // Handle incoming messages
      }
  Fix: switch on frame.type(): TEXT_MESSAGE (0x30) deserialize TextMessage and
  pass to onMessageReceived; MESSAGE_ACK (0x31) resolve the PendingAck in
  pendingAcks; GROUP_MESSAGE (0x33) route to the group chat. Deduplicate by
  messageId (MessageDeduplicator already exists and is tested - reuse it).

[E5] TransferManager: all four wire methods are empty -> transfers send zero bytes
  File: core/transfer/TransferManager.java
      private void sendFileRequest(...)   { // Send FILE_REQUEST frame }
      private void sendFileAccept(...)    { // Send FILE_ACCEPT frame }
      private void sendFileChunk(...)     { // Send FILE_CHUNK frame }
      private void sendFileComplete(...)  { // Send FILE_COMPLETE frame }
  Also empty: onTaskStart, onTaskComplete, onTaskProgress, onTaskFail,
  handleFileRequest, handleFileAccept, handleFileResume, reportProgress,
  getTransfer, getActiveTransfers, getQueueSize, getRunningCount.
  sendFile() already computes SHA-256, builds TransferMetadata and queues the
  task correctly - it just never emits a frame.
  Fix: implement the FILE_* frame handlers using types 0x40 REQUEST,
  0x41 ACCEPT, 0x43 CHUNK, 0x45 COMPLETE, 0x48 RESUME. Chunk size comes from
  config.transfer.chunkSize (65536). Receive side must reassemble to
  downloadDir and verify against the sender's SHA-256.
  NOTE: the transport is already proven to handle 64KB chunks and 512KB
  payloads (P2PFrameDeliveryTest), so no transport work is needed here.

[E6] No encryption at all - TLS is dead code, never invoked
  File: core/security/TlsContextManager.java
  Findings:
    - loadOrGenerateIdentity() generates an Ed25519 keypair and parses the
      public/private keys, but NEVER stores localPrivateKey/localCertificate
      into any KeyManager, and the parsed publicKey is discarded unused.
    - initializeSslContext() calls SSLContext.getInstance("TLSv1.3") then
      sslContext.init(null, null, new SecureRandom()) - i.e. DEFAULT trust
      managers, no client cert auth. It will not authenticate a peer.
    - grep confirms TlsContextManager / SSLEngine / SSLContext are referenced
      NOWHERE outside that one file. It is never constructed by DesktopService.
    - ConnectionManager uses plain SocketChannel, never an SSLEngine.
  Net effect: all LAN traffic is plaintext. config.security.tlsVersion and
  requirePairing: true in config.yaml are ignored entirely.
  Fix: generate a self-signed Ed25519 cert with BouncyCastle bcpkix (already a
  dependency), build a KeyManager holding the private key + cert chain, wire
  TlsContextManager into DesktopService, and wrap the SocketChannel in an
  SSLEngine inside ConnectionManager (handshake as a new OP_CONNECT-like
  interest, then hand the channel to the existing read/flush logic).
  Also fix KeyPairGenerator: its deviceId derivation is a comment, and it is
  referenced nowhere outside TlsContextManager.

[E7] PairingManager is entirely empty
  File: core/security/PairingManager.java
  All methods empty, including initiatePairing() which MainWindow calls. The UI
  passes a hardcoded "remote-public-key" string (MainWindow.java ~385).
  Fix: implement PAIR_REQUEST (0x50) / PAIR_ACCEPT (0x51), fingerprint
  verification, and TrustStore persistence. MainWindow must pass the peer's
  real advertised public key from DeviceInfo, not a placeholder.

7. THINGS THAT WILL TRIP UP A NEW CONTRIBUTOR
================================================================================

  - The build prints ERROR lines from ErrorHandlerTest on every successful run.
    Those are the test exercising error handling, not build failures. Look for
    "BUILD SUCCESS" / "Tests run".
  - module-info.java exists (JPMS module com.labconnect.core) but the fat jar
    runs on the classpath, so module boundaries are NOT enforced at runtime.
  - Java target is 17, JDK is 21, JavaFX 21.
  - ConnectionManager.sendFrame dispatches onto a 4-thread pool, so frame
    ordering across frames is NOT guaranteed. Do not assert strict ordering in
    tests - assert set equality.
  - heartbeatInterval matters for tests: use a large value (30s) so the stale-
    detection timer does not close connections mid-assertion.
  - Allocate test ports with new ServerSocket(0), never a fixed port, and do
    not close/recreate a ConnectionManager mid-test on a shared port.
  - config.yaml is read from the CURRENT WORKING DIRECTORY. Launching two
    instances from one directory makes them share settings. Use one directory
    per instance.
  - DiscoveryListener needs SO_REUSEADDR (already set) or a second instance on
    the same host cannot bind port 50001.
